## Strings, memory and GC: summary

- Fresh `strconcat`: threaded uses 645.3M instructions versus 879.9M for Lua, but sampled Lua-accounted peak is 26,046 versus 14,754 KiB.
- High confidence: the collector's sweep procedure and debt reset match Lua; the eight-byte short-header overhead strongly shifts its phases, and the copied result is counted where Lua's external buffer is not. Other layout differences still affect the exact trajectory.
- A realistic first target is ~4,241 KiB less **accounted** peak at the result boundary, conditional on a correct zero-hot-overhead external-string design. This is not a promise of the same physical-memory reduction or of closing the whole gap. No safe sweep-only fix was identified.
- The old 3× intern-chain claim is disproved for the isolated cases below; retire it, rather than optimize for it.

## Measurements

- `0738e32`, Linux x86-64, optimized builds, isolated `bench/micro.lua strconcat`; 5 rotated runs, `perf stat -e instructions:u` (millions, min/median/max):

  | Instructions | 645.284/645.298/645.300 | 667.023/667.029/667.108 | 879.839/879.852/879.959 |
  | Unmodified harness final `collectgarbage("count")`, KiB | 26,590.9 | 26,590.9 | 14,754.3 |
  | Sampled peak, KiB | 26,045.8 | 26,045.9 | 14,754.1 |
  | Interned strings at sampled peak | 320,739 | 320,738 | 244,461 |

- Sampling was a separate instrumented build/script, every 1,000 loop iterations and before/after `table.concat`; 3 runs each. `count` is allocator-accounted memory, **not** RSS and not an instantaneous allocation peak. Instrumentation and extra Lua code change GC timing, so do not equate its numbers with the unmodified harness or the older 25,448/14,012 KiB trace.
- Independently measured process high-water RSS for the unmodified benchmark: threaded 36,352–37,760 KiB, switch 37,332–37,848 KiB, reference 28,612–28,920 KiB (3 runs). This includes raw buffers and allocator overhead.
- Full-GC control, with the 200,000-element table still rooted and before concatenation: threaded 200,264 strings / 16,922.2 KiB / 524,288 buckets; reference 200,264 / 13,307.9 KiB / 262,144 buckets. Of the 3,614.3 KiB difference, approximately 1,565 KiB is the extra 8 bytes per short-string header and 2,048 KiB is the extra bucket half; small object/layout differences explain the remainder. `checkSizes` correctly does not shrink either table at these occupancies. The control is a distinct script and perturbs earlier pacing.
- Chain probe: fixed seed `0x12345678`, 256 buckets, GC stopped, one million `string.sub` lookups; 0–24 deliberately colliding predecessors, 3 perf runs. Marginal instructions/link for **different-length** predecessors: threaded 5.00, switch 5.00, reference 6.00. For same-length unequal keys: 12.13 / 12.13 / 29.00, including each implementation's byte comparison. The table remained at 256 buckets in both; these are not universal costs for all string workloads.
- Scratch reference controls: replacing external-buffer transfer with a copy/no explicit buffer step changes sampled peak 14,754.1 → 18,995.0 KiB (+4,240.9), same 244,461 final interned strings. Adding eight bytes before reference short-string data changes its GC trajectory substantially: sampled peak 19,817.4 KiB and a later major→minor transition, not the port's exact trajectory. Padded and padded+copy controls each passed unmodified PUC `gc.lua` and `gengc.lua` standalone with the wrapper's `_soft/_port/_nomsg` settings. These controls are diagnostic, not proposed implementations.
- A separate **diagnostic-only** port prototype paces and marks short strings as if their headers were eight bytes smaller while reporting the actual 32-byte allocations. With the sampled script, threaded peak drops 26,045.8 → 19,984.0 KiB, interned strings 320,739 → 221,698, and buckets 524,288 → 262,144 (3 runs). On the unmodified harness, threaded final heap falls 26,590.9 → 19,985.6 KiB and instructions rise 645.298 → 646.098M; switch ends at 19,985.6 KiB / 667.870M. Both modes pass standalone unmodified PUC `gc.lua` and `gengc.lua`. This is a causal control, not a conformant fix: it intentionally misstates the actual work/bytes used for GC pacing, and passing these tests does not establish semantic equivalence.

## Causes

- Both `src/kernel/gc_run.odin` and reference `lgc.c`: atomic flips white; if not returning to generational minor mode, `entersweep` calls `sweeptolive` to place the cursor after the first survivor. Objects subsequently prepended to `allgc` are skipped until a later collection. A normal `singlestep` visits at most `GCSWEEPMAX=20` objects and reports 20 units even for phase transitions; fast/full sweep can visit the whole list.
- Default table size is 48 bytes in both, hence a basic incremental step uses 9,600 bytes and 2,400 work units: usually 120 sweep single-steps × 20 objects. Allocations reduce debt; frees credit their **actual** size while sweeping, but `incstep` resets the next debt to 9,600 after a nonterminal step, rather than carrying free credits forward. The atomic step ends its basic step early. The minor→major `minor2inc` sets 9,600, but the caller's unconditional `setminordebt` then overrides it with the minor percentage of the major base, in both implementations.
- After `allgc`, `finobj`, and `tobefnz`, `checkSizes` runs at `GCSswpend` (also after a minor cycle), shrinking by half only when `nuse < buckets/4` and not in emergency GC. After finalizers, the cycle enters pause; `setpause` uses `max(0, coded_pause × marked − actual_live_bytes)`. The default pause is 250%. Do not silently change these rules or fabricate debt: `collectgarbage` and finalizer timing are observable.
- Deterministic stopped-GC control: create 4,000 rooted strings plus garbage, then force eight `collectgarbage("step",0)` steps. Both begin with 12,218 interned strings; both take 29 single-steps to propagate, 4 to enter sweep, then five batches of 120, followed by 17 to pause. Both progress 12,217 → 10,617 → 9,017 → 7,417 → 5,817 → 4,218; neither shrinks 16,384 buckets. Each 1,600-string reclamation credits 63,200 port bytes versus 50,400 reference bytes, exactly 8 extra per string. Pause debt is 191,258 versus 140,646 because marked/live bytes differ. This is direct evidence against a misplaced sweep or incorrect 20-object limit.
- In the sampled workload the last normal major atomic begins at 157,405 port interned strings versus 202,406 reference; after that sweep completes the counts are 153,887 versus 199,841, and while paused they grow to 320,739 versus 244,461. At result creation port's 4,342,927-byte counted allocation takes debt negative and starts propagation; reference's external result stays uncounted, and its explicit byte charge still leaves positive debt. The shadow-pacing control shows the extra short-header charge is a major driver of this phase shift and the extra bucket doubling. Other allocation/layout differences still prevent an exact event-for-event match; the padded-reference control rules out attributing the entire trajectory uniquely to one factor.
- Reference `luaL_pushresult` transfers the raw buffer and calls `lua_gc(L, LUA_GCSTEP, len)` in **bytes** after closing the emptied box; this step temporarily permits GC even when user-stopped. Port `aux_pushresult` copies via `api_pushlstring` and has no corresponding explicit buffer charge. Adding the step alone to the counted copy would double-charge the result and is not an equivalent fix.

## Levers

1. **Correct external ownership + buffer transfer, only if hot paths stay unchanged.** Preserve direct inline bytes for known internal/short strings; isolate an external-only representation/accessor at already-discriminated cold long-string boundaries. A uniform pointer/load or per-string `is_external` check repeats the dead-end prototype (+8M `strconcat`, +24M `tablechurn`), so reject it. Whether all generic accesses can avoid that cost is unproven. The measured accounted gain at this boundary is ~4,241 KiB; the buffer is still physically allocated, although the temporary duplicate and copy disappear. Subsequent GC timing may help or hurt.
   - Mirror `lua_pushexternalstring`: borrowed fixed buffers have no release callback; owned buffers get exactly one `(ud, s, len+1, 0)` callback on reclamation/state close or construction failure, including emergency GC. Validate length and terminating NUL. Keep the external object rooted before checks; never rely on `defer` across `longjmp`.
   - Short external strings initially remain external long variants. Generic equality/hash/lookup must compare across short/long variants; only a new table-key insertion normalizes short external content to an interned key, rooting it through allocation. Normalization must not free a still-live external object. Coordinate with the tables/globals analyst.
   - For aux buffers, resize to `len+1`, write NUL, detach/zero the to-be-closed box exactly once, transfer owner, root the result, close the box, and charge `GCSTEP(len)` as reference does; retain box ownership if resize fails. Preserve collector stop bits, finalizer/allocator callback and OOM behavior.
2. **Compact representation feasibility, not the old 24-byte layout.** A dispatch-free 24-byte header with the same direct 64-bit length and inline data can move the intern link to an index sidecar. But a portable sidecar needs a pointer and a 32-bit next index per slot: ~12 bytes/slot, even with separate packed arrays, and 32-bit bucket heads. At 200,264 strings and 262,144 slots/buckets, savings of 8 bytes/string and 4 bytes/bucket are outweighed by sidecar storage by ~484 KiB; the extra dependent load also risks instructions. Exactly sized slots save only ~242 KiB and require frequent growth/reindexing. These are arithmetic estimates, not measurements; allocator slack and emergency-GC safety worsen the case. A bounded/compressed-pointer arena needs an explicit proof for arbitrary embedder allocations and full-length strings, not a 4-GiB cap. Do not retry the old short/long length dispatch (+52M `strconcat`, +329M `tablechurn`).
3. **No speculative pacing change.** The extra garbage and persistent oversized bucket array are real, but the matching sweep trace provides no reference-conformant tuning fix. Investigate remaining layout/allocation differences before claiming one. More aggressive shrink/pause parameters or the measured shadow accounting control would change collection pacing; not acceptable as a shortcut even though the control keeps `count` honest and passes the two GC files.
4. **Intern chain: retire the 3× claim.** The isolated mismatched-length link is already 5 versus 6 instructions; same-length comparisons favor the port. Keep the probe as a regression benchmark, not a priority optimization. Other collision distributions and allocation/growth are separate questions.

## Open questions

- Is complete Lua 5.5 external-string embedding API compatibility worth prioritizing even if a no-regression representation cannot be found? For performance alone, defer it unless the gated prototype beats the already-measured dead end.
- Which non-header allocation/marking differences account for the remainder of the phase shift after the reference padding control? No exact single-cause fix is established yet.
